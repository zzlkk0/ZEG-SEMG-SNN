### 1.2 窗口标注纯度规则

`prepare_db5.py::label_window()`:

```python
def label_window(labels, exercise_purity):
    if np.all(labels == 0):
        return 0                      # 100% rest -> 标记为 rest
    nonzero = labels[labels > 0]
    values, counts = np.unique(nonzero, return_counts=True)
    label = values[argmax(counts)]
    if counts[index] / len(labels) >= exercise_purity:  # 默认 0.8
        return label                  # >=80% 多数手势样本 -> 标记为该手势
    return None                       # 否则丢弃
```

和 spec 1.3 节描述的论文规则("窗口内 ≥80% 样本标为该手势才标记为该手势;100%标为
rest 才标记为 rest;不满足则从训练/测试中剔除")逐字对照,**完全一致**
(`exercise_purity` 默认值就是 0.8)。**不需要重新按论文规则准备数据**,现有
`data/processed/*.npz` 已经是论文规则下的产物。

## 2. 时域投票后处理(spec 2.1)

### 2.1 算法与实现

`voting.py`(纯 numpy,无 torch 依赖)实现了两种投票方式:

- **`paper_style_vote`**(主要口径):按 spec 描述的语义实现——逐窗遍历,如果某窗口
  预测和当前"已接受"标签不同,只有当**下一个窗口的预测也支持这次切换**(即连续两个
  窗口一致)才真正切换,否则视为孤立单点跳变,丢弃、沿用上一个已接受标签。这是一个
  1 窗口(100ms)前瞻滤波,host 端需要缓冲多一个窗口的延迟才能应用。
- **`two_window_debounce_vote`**(对照口径):项目里 `evaluate_checkpoint.py` 已有的
  纯因果版本(不看未来,只看已经出现过的候选是否连续两次一致才切换),列出来做对比,
  说明两种"需要连续两窗口一致才切换"的实现方式,因果 vs 前瞻,结果并不相同。

### 2.2 结果(全 11,276 测试窗)

| 口径 | accuracy | macro-F1 | gesture-accuracy |
|---|---:|---:|---:|
| 逐窗严格(基线,无后处理) | 83.9305% | 0.6561 | 57.9432% |
| **paper_style_vote(前瞻投票)** | **84.3828%** | **0.6693** | **58.9619%** |
| two_window_debounce_vote(因果投票,对照) | 83.6201% | 0.6611 | 58.2100% |
| ±200ms 容差(补充口径,见下方假设声明) | 85.8904% | -- | -- |

**如实报告**:前瞻投票(`paper_style_vote`)带来 **+0.4527 个百分点**的提升,是三种
后处理里唯一确定有改善的。因果投票(`two_window_debounce_vote`)反而让精度**下降**
了 0.3104 个百分点——这个对照结果说明"要求连续两窗口一致才切换"这个思路本身不是
万能的,**是否前瞻**(用未来一步信息 vs 纯因果)是决定它有没有效果的关键因素,不能
简单假设"加了投票就会变好"。

±200ms 容差口径达到 85.8904%,但这是一个更宽松的评估口径(允许预测和窗口±200ms
范围内任意真实标签匹配即算对),按 spec 要求**只作为补充口径,不替代上面两个主口径**。
论文没有公开这个指标的精确帧级伪代码,这里用的假设是:"一个窗口的预测,只要和同一
受试者、±200ms(±2 个 100ms 跳步窗口)范围内任意窗口的真实标签相同,就算正确"——
这是一个较宽松的重建,数值仅供参考。

## 3. 稀疏度正则化 Pareto 扫描(spec 2.4)

### 3.1 方法

- 从现有部署基线 `delay62_finetune/best.pt` 热启动微调(不是从零训练),拓扑、
  权重量化位宽、延迟范围、衰减常数全部不变。
- 在 `spike_rate_loss`(分类损失,已经是论文式的发放率回归)基础上加一项
  `lambda_sparsity * mean(四层脉冲发放率)` 作为 L1 风格稀疏度惩罚,鼓励整体活动更稀疏。
- 稀疏度按 spec 要求,以**分组大小=1**(逐脉冲,不按论文的 4-脉冲分组)、按各层
  神经元数加权的口径统计:`sparsity = 1 - (总活跃脉冲数/总可能脉冲数)`。
- 单次 1 epoch 校准扫描确认了正则强度的敏感范围(见下表),据此选择了一组更细的
  多 epoch(最多 10 epoch,`patience=5`)扫描点。

### 3.2 敏感范围校准(1 epoch,粗扫)

| lambda | test accuracy | sparsity(group=1) |
|---:|---:|---:|
| 0.0(对照)| 83.97% | 92.12% |
| 0.001 | 83.74% | 93.12% |
| 0.003 | 82.83% | 94.65% |
| 0.01 | 79.46% | 97.19% |
| 0.03 | 71.38% | 98.81% |

**关键背景事实**:这个 Delay-SNN 基线本身**在没有任何显式稀疏正则的情况下,
已经天然非常稀疏**(group=1 口径下约 92% 稀疏,即只有约 8% 的可能脉冲位置真正
发放)。这是因为 `spike_rate_loss` 本身的目标发放率就很低(正确类 0.2、错误类
0.03,对输出层),加上 LIF 积分-发放-复位机制天然会抑制过度发放。这意味着**在
不明显伤害精度的前提下,稀疏度正则能再挤出来的"免费"空间并不大**——从校准数据看,
lambda 超过 0.003 左右,精度开始明显下滑;超过 0.01,精度掉了 4 个百分点以上,
不再是"轻微牺牲"。

### 3.3 完整 Pareto 扫描结果(多 epoch,收敛后)

从 `delay62_finetune/best.pt` 热启动,每组最多 10 epoch、`patience=5`,按验证集
`分类loss + lambda*(1-sparsity)` 早停选 checkpoint。**全部 6 组都跑到了收敛
(只有 λ=0.01 在第 7 轮触发早停,其余都跑满 10 epoch)。**

| lambda_sparsity | test accuracy | macro-F1 | gesture-accuracy | sparsity(group=1) | best_epoch |
|---:|---:|---:|---:|---:|---:|
| 原始基线(未微调)| 83.9305% | 0.6561 | 57.9432% | 91.93% | -- |
| **0.0(对照,继续微调但无正则)** | 83.4516% | 0.6429 | 56.4395% | 92.12% | 10 |
| 0.0005 | 83.3097% | 0.6426 | 56.8276% | 94.03% | 10 |
| **0.001** | 83.4072% | 0.6433 | 56.7305% | **95.30%** | 10 |
| 0.002 | 83.1146% | 0.6331 | 55.4693% | 97.19% | 10 |
| 0.005 | 82.5027% | 0.6205 | 53.9898% | 98.21% | 10 |
| 0.01 | 80.9773% | 0.5822 | 50.4730% | 98.70% | 7(早停) |

**关键发现,如实报告(包括不好看的部分)**:

1. **λ=0(对照组)本身就比原始基线掉了 0.4789 个百分点**(83.9305%→83.4516%)。
   这不是稀疏正则的代价——纯粹是"用全新 Adam 状态继续微调"这个动作本身带来的漂移
   (原始 checkpoint 是它自己训练轨迹里验证集最优的一点,重新热启动、重置优化器动量,
   不保证在有限 epoch 内重新找到同样好或更好的点)。**所以后面每个 lambda 的代价,
   应该对照"83.4516%"这个继续微调对照组,而不是原始的 83.9305%**,否则会把微调噪声
   误算成正则化的代价。
2. 以对照组(83.4516%)为基准:
   - λ=0.0005~0.001 区间,精度几乎不变(±0.14pp 以内),但 sparsity 从 92.12% 提到
     93.9%~95.3%,是目前看起来**性价比最好的区间**。
   - λ=0.002 开始,精度掉了 0.34pp,换来 sparsity 到 97.19%。
   - λ=0.005 掉了 0.95pp,λ=0.01 掉了 2.47pp——超过 λ=0.002 之后,代价明显加速上升,
     不再是"轻微牺牲"。
3. **这个分支本身天然就非常稀疏**(未加任何正则时已经 91.93%~92.12%),这是
   `spike_rate_loss` 低目标发放率(0.2/0.03)加上 LIF 硬复位机制的自然结果。这意味着
   稀疏度正则能挤出的"免费"空间本来就不大——从 92% 提到 95% 左右基本不花代价,
   但再往上每提 1~2 个百分点,精度代价会越来越陡。

### 3.4 定点(RTL 等效)口径下的验证

上面第 3.3 节的数字都是**浮点**口径(训练/验证时用的评估),和项目里报告基线
83.9305% 用的是同一个口径,可以直接和历史数字比较。但最终真正跑在硬件上的是
**INT8 权重 + Q8 膜电位 + 230/256 衰减**的完全定点版本——这个口径下的数字不一定
和浮点口径一致,所以对两个候选 checkpoint(λ=0.001、λ=0.002)额外做了一次完整的
定点导出+全测试集评估(见第 4 节的方法),得到:

| lambda_sparsity | 浮点 test accuracy | **RTL 定点 accuracy** | 定点相对浮点的落差 |
|---:|---:|---:|---:|
| 原始基线 | 83.9305% | 83.0702% | -0.8603pp |
| 0.001 | 83.4072% | 82.8751% | -0.5321pp |
| 0.002 | 83.1146% | 81.9085% | -1.2061pp |

**如实报告**:λ=0.001 在浮点口径下看起来"几乎免费",但过完整的定点量化之后,
RTL 等效精度(82.8751%)比原始基线的 RTL 等效精度(83.0702%)还是低了 0.1951pp——
量化本身的落差幅度(浮点→定点)在不同 lambda 之间也不完全一致,不能只看浮点数字
就下结论。**这个 RTL 定点数字,才是真正该用来做部署决策的数字**,浮点 Pareto
表格只能作为训练阶段的中间参考。

## 4. 权重格式兼容性验证(spec 2.5)

复用现有部署脚本 `semg_snn_nexys4ddr_vivado/scripts/export_fixed_point.py`,**未做
任何修改**,直接指向新 checkpoint 重新导出:

```bash
python scripts/export_fixed_point.py \
  --checkpoint <新checkpoint路径> \
  --test-data .../data/processed/test.npz \
  --output <输出目录>/weights \
  --vectors <输出目录>/vectors
```

**验证方法**:先用现有基线 `delay62_finetune/best.pt` 重新跑一遍这个导出流程
(而不是直接读现成的 `weights/manifest.json`),确认从权重到 RTL 等效整数推理的
**全流程**能不依赖任何缓存结果、从头精确复现已知数字:

```
rtl_integer 精度(重新导出+重新推理): accuracy=0.8307023767293367
已部署 manifest.json 记录的数字:      accuracy=0.8307023767293367
```

**逐位一致**。这证明了导出脚本本身是确定性、正确的,可以直接拿去用在本次重训出的
新 checkpoint 上,不需要修改脚本、不需要改动 HLS/RTL——因为:

- 拓扑没变(96→64→128→64→13,前三层各一个整数延迟)
- 训练时用的仍然是 `PaperSNNWithDelays`(权重结构、参数名完全一致)
- 权重量化位宽、延迟范围(0–62)、膜电位 Q8 格式、`beta=230/256`、RNE 舍入、硬复位——
  这些都是导出脚本自己算出来的,不依赖训练时用了什么 loss,只要模型结构不变就自动兼容。

**对稀疏正则候选 checkpoint 重复同样的验证**(λ=0.001、λ=0.002),导出脚本
**原样运行,零修改**,成功产出 `weight_scales`(4 个,每层一个)、`thresholds_q8`

**结论:两个候选 checkpoint 都能被现有导出脚本正确处理,产出的定点格式和现有部署

方式(硬复位)在导出脚本里是写死的常量,不依赖 checkpoint 内容,自动保持不变。
延迟范围检查(`0<=delay<=62`)在导出时会自动校验,两个候选都通过,没有触发任何
形状/范围校验错误。
